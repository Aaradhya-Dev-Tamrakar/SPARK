## task_2026-08-21_002

**Summary:** Track 1 (Novelty Claim 1 narrowing): formal 2023-2026 search finds no MCU-class system combining SPARK's exact pattern (continuous software threshold gate + on-device CNN confirmation, both on one MCU, no gateway/server offload). Proposed narrowed Claim 1 sentence delivered; existing NLM notebook 2c00f5a4 sources checked (none cover this specific axis).

### Research question
Does published 2023-2026 literature contain an MCU-class (ESP32/Arduino/Cortex-M tier) two-stage gated fall-detection pipeline matching SPARK's Claim 1 (hardware/software threshold gate -> on-device CNN confirmation), and if so, what narrowed claim-1 wording survives against it?

### Bottom line
Yes, prior art exists for "two-stage/gated" fall detection generally (confirmed, extending v18's finding), but no 2023-2026 source found combines SPARK's specific triad: (a) a continuously-sampled *software* magnitude+duration threshold gate, (b) a subsequent CNN confirmation, (c) both stages executing on the *same* single MCU with zero offload to a gateway/server for the classification decision. The closest works split on one of these three axes. Claim 1 should be narrowed to that specific combination rather than "no gated system exists."

### Key findings

- **Finding:** Threshold-gate + CNN "two-stage" fall detection is an established pattern with a real 2021 precedent, not a 2023-2026 gap.
  - **Evidence:** Xu, Se & Liu's SHFFD system runs a threshold-based module (TBM) on an MSP430F149 wearable node, but explicitly offloads the "more powerful CNN" to a **server** for the final decision — architecturally: MCU-tier gate + server-tier ML.
  - **Source:** T. Xu, H. Se, J. Liu, "A fusion fall detection algorithm combining threshold-based method and convolutional neural network," *Microprocessors and Microsystems*, vol. 82, p. 103828, 2021. (Confirmed via ResearchGate abstract + citing paper's reference list; ScienceDirect DOI page inaccessible for full text — abstract-level confidence only.)
  - **Confidence:** Established (existence/architecture); Supported inference (that no on-device successor exists — absence-of-evidence, see limitations).
  - **Relevance to SPARK:** Sets the baseline "gated" idea predates 2023 — SPARK cannot claim the *general* threshold+ML gating idea as novel (consistent with v18). But it also gives SPARK a concrete architectural differentiator: SPARK never leaves the MCU for classification; this 2021 system does.

- **Finding:** A recurring 2023-2025 alternative to gating is a single always-on MCU-resident CNN with no preceding threshold stage, on MCU tiers directly comparable to SPARK's.
  - **Evidence:** Yu et al.'s TinyCNN runs continuously on an Arduino Nano 33 BLE Sense, 37 ms latency, >99%/>98% sensitivity/specificity on KFall/SisFall — "two-stage" in its own title refers to internal CNN feature-extraction design, not a hardware/software pre-gate. Hu et al.'s MicroFallNet (ScienceDirect version) runs continuously on ESP32, 30.3 ms inference, 97.91%/97.86% geometric-mean accuracy on UMAFALL/FallAllD. A same-titled MicroFallNet variant on ResearchGate reports ESP32-S3 + MPU6050 (SPARK's exact chip+IMU pairing), 14 ms/2000 ms window, 9,623-byte model, 97.8%/97.4% sensitivity on SisFall/self-collected data — but with different datasets/numbers than the ScienceDirect version, so these may be two distinct papers sharing a name rather than one paper (unresolved, flagged below). An IEEE-indexed conference paper ("Wristband Fall Detection System Using Deep Learning," IEEE Xplore doc 9846023) likewise runs a continuous DL model on ESP32 with no gate, 96.55% accuracy.
  - **Source:** Yu et al., *Measurement* (Elsevier), 2023/2024, ScienceDirect DOI pii/S1746809423007589; Hu et al. 2025a, ScienceDirect DOI pii/S1574119225000355; MicroFallNet (ESP32-S3 variant), ResearchGate pub. 390407102 (2025); IEEE Xplore document 9846023.
  - **Confidence:** Established for each individual paper's own reported design; Unresolved on whether the two "MicroFallNet" listings are one paper or two.
  - **Relevance to SPARK:** These are SPARK's closest same-MCU-tier competitors on model size/latency, but none gate the CNN behind a threshold — they run it on every window. This is exactly the axis SPARK's Layer 1 (skip CNN below 2.5g/300ms) claims to differ on: power savings from *not* running the CNN on most windows. None of these four papers report or claim that saving.

- **Finding:** MCU-class hardware-level low-power wake gating exists, but via the IMU's native wake-on-motion interrupt, not a continuously-sampled software threshold running in the MCU's own ISR (SPARK's actual design, per tracker §2.5 and chapter3_related_theory.tex).
  - **Evidence:** A 2025 wearable system configures an LSM6DSO IMU in "Wake-on-Shake" mode with an STM32WB5MM MCU held in STOP/STANDBY, woken via interrupt only on motion (~5 mA average current), then running its detection algorithm.
  - **Source:** "Wearable Fall Detection System with Real-Time Localization and Notification Capabilities," *Sensors* (MDPI) 2025, PMC12196599.
  - **Confidence:** Established.
  - **Relevance to SPARK:** This is the nearest true "hardware gate on an MCU" analogue found, but SPARK's Layer 1 is explicitly a **software** threshold evaluated on a continuously-running 200 Hz ISR loop (no MCU sleep state), not an IMU-native interrupt-driven wake. That is a real, defensible distinction to name explicitly in the narrowed claim rather than eliding it — reviewers who know STM32/nRF wake-on-motion parts could otherwise read SPARK's "hardware-gated" language as claiming this exact mechanism, which it does not use.

- **Finding:** The threshold-gate-then-heavier-model pattern also appears in 2025-2026 systems that split the two stages across *different network hops* (node -> gateway/cloud), reinforcing that "same-chip, no-offload" is the differentiator, not gating itself.
  - **Evidence:** A LoRa-based system runs a threshold check on the wearable node (20 Hz sampling, wakes and transmits a 4 s window only if magnitude threshold exceeded) and a CNN-LSTM classifier that "refines" the decision, evaluated alongside per-device and gateway/cloud cost tables — indicating the CNN-LSTM stage is not confirmed to run on the wearable MCU itself. A 2026 vision-fusion system similarly uses an acceleration threshold to *activate a camera*, then runs YOLOv5 + an 8-layer CNN — necessarily off-MCU compute given camera + YOLOv5.
  - **Source:** "Energy-Efficient Fall-Detection System Using LoRa and Hybrid Algorithms," *Biosensors* (MDPI), May 2025, PMC12109012; "Real-time, mobile-compatible, and low-cost fall detection system with deep learning," *Signal, Image and Video Processing* (Springer), 2026.
  - **Confidence:** Supported inference (LoRa paper's CNN-LSTM execution location is not explicitly stated as node vs. gateway in the retrieved abstract/excerpts — flagged as a gap, not confirmed either way); Established for the vision-fusion paper's off-MCU compute (YOLOv5 cannot run on ESP32/Cortex-M tier hardware).
  - **Relevance to SPARK:** Both reinforce that a threshold-gate-into-heavier-model pattern is common, but the heavier model typically runs somewhere with more compute than the gating node itself. SPARK's choice to keep Layer 2's CNN on the *same* ESP32-S3 as Layer 1, with zero network dependency for the classification decision, is the load-bearing distinction.

- **Finding:** A cross-tier boundary case exists — genuinely on-chip 2-stage hybrid ML fall detectors — but on FPGA/RISC-V SoC, not commodity MCU.
  - **Evidence:** "Vigil" implements a hybrid probabilistic-CNN + k-NN fall detector as a custom RISC-V SoC on FPGA, both stages on the same chip.
  - **Source:** IEEE Xplore document 10483334 (2024 IEEE conference publication).
  - **Confidence:** Established.
  - **Relevance to SPARK:** Confirms same-chip two-stage designs exist, but at a hardware tier (custom FPGA SoC) far above ESP32-S3's off-the-shelf $5-class MCU — supports narrowing Claim 1 to commodity MCU-tier hardware specifically, since "same-chip 2-stage" alone is not novel once FPGA-tier work is included.

## task_2026-08-21_003

**Summary:** Formal IEEE/Scopus-oriented pass on local/edge-computed SHAP-equivalent explainability for wearable fall/HAR classifiers. Found IEEE-indexed and Scientific-Reports-indexed prior art applying SHAP/KernelSHAP to wearable/smartphone HAR (general activities, not fall-specific in the SHAP cases) as offline post-hoc analysis — none combine gradient×input attribution + execution on a separate local non-cloud gateway + fall-detection clinical framing. Proposed narrowed Claim 3 sentence and full evidence table below.

### Research question
Track 2 (Action #26, §2.3): Is there IEEE Xplore/Scopus/ACM-indexed prior art specifically on *local/edge-computed* (non-cloud) explainability — gradient-based (X×∇X, matching SPARK's `CnnShapExplainer`) vs. KernelSHAP vs. other local-XAI methods — for wearable fall/activity classifiers on resource-constrained gateways? If so, what's the closest prior art and how should Claim 3's wording be narrowed?

### Bottom line
Real, citable prior art exists (confirming v18's finding and Action #26's premise), but it clusters into two groups that each miss at least one element of SPARK's specific design: (1) SHAP/KernelSHAP applied to wearable/smartphone HAR or fall detection, but as **offline, post-hoc research analysis** (not a real-time deployed local-gateway pipeline), and mostly on **general HAR classes, not fall detection specifically**; (2) general "edge XAI" literature establishing that **gradient-based methods are computationally far cheaper than KernelSHAP** (supporting SPARK's engineering choice) but not applied to wearable fall detection or framed around a **distinct local companion-device gateway** (as opposed to the wearable itself, or the cloud). No source found that jointly demonstrates gradient×input attribution + execution on a separate local non-cloud gateway + fall-event clinical reporting. This is a narrower, defensible gap than the original broad claim, consistent with Action #26's recommendation.

### Key findings

**Finding 1: SHAP/KernelSHAP has already been applied to wearable/smartphone HAR in IEEE-indexed venues, but as offline analysis, mostly on general activity classes, not fall detection.**
- Evidence: A 2025 unified survey (Kundu et al., "Explainable Human Activity Recognition: A Unified Review of Concepts and Mechanisms," arXiv:2604.09799, USF/Cal Poly) catalogs this cleanly. Liu, Perumal, Cheng & Xie, "Enhanced human activity recognition framework for wearable devices based on explainable ai," *2024 IEEE International Symposium on Consumer Technology (ISCT)*, pp. 385–391 — applied a **kernel-based SHAP explainer** to a CNN–LSTM trained on the UCI HAR dataset (walking/sitting/standing/etc., not falls) to analyze tri-axial accelerometer feature contributions. Arul, Karthikeyan & Ramanujam, "Revealing the importance of local and global interpretability in smartphone based human activity recognition," *2024 IEEE Students Conference on Engineering and Systems (SCES)* — SHAP + XGBoost on UCI HAR smartphone accelerometer/gyroscope data.
- Source: arXiv:2604.09799 (survey, citing the above IEEE papers directly); IEEE Xplore entries for ISCT 2024 and SCES 2024.
- Confidence: Established (IEEE-indexed venues, survey cross-confirms).
- Relevance to SPARK: Confirms v18's finding that SHAP-for-wearable-HAR prior art is real. But neither paper is fall-detection-specific, neither specifies a real-time on-device/gateway deployment (both read as standard train-then-explain research pipelines), and neither uses gradient×input — they use KernelSHAP/TreeSHAP variants. This is exactly the kind of prior art Action #26 anticipated a panel member finding, and it does invalidate the broadest form of Claim 3 ("no existing system applies SHAP to wearable fall/activity data").

**Finding 2: SHAP has also been applied specifically to fall detection (smartphone-based), but as offline post-hoc interpretability analysis in MATLAB, not gradient-based, and not framed as a local-vs-cloud gateway architecture.**
- Evidence: Guo & Nakayama, "A Feature Engineering Method for Smartphone-Based Fall Detection," *Sensors* 2025, 25(20), 6500 (MDPI, Scopus-indexed). Uses KNN/SVM on hand-engineered statistical features from smartphone accelerometer data (UniMiB SHAR, MobiAct, FARSEEING datasets); Section 7 runs a SHAP-based interpretability analysis (beeswarm plots, dependency plots, force plots) computed offline in MATLAB on a MacBook Air M1, purely for research-paper analysis, not delivered as part of a live per-event clinical output.
- Source: DOI 10.3390/s25206500.
- Confidence: Established.
- Relevance to SPARK: This is the closest single-paper analog to "SHAP + fall detection," but it differs from SPARK on three axes simultaneously: (a) classical ML (KNN/SVM) not a CNN, so SHAP here is standard KernelSHAP/model-agnostic, not gradient×input; (b) SHAP is a one-time offline research artifact, not a per-event runtime output delivered to a caregiver; (c) there is no separate "gateway" — the smartphone is both sensor and (implicitly) analysis platform, so there's no local-non-cloud-gateway architectural claim being made. SPARK's design (MCU-tier wearable → BLE → distinct laptop gateway with NPU/iGPU running gradient×input per fall event, feeding an auto-generated clinical PDF) is not what this paper describes.

**Finding 3: Gradient-based attribution (saliency, integrated gradients, Grad-CAM, and gradient×input/DeepSHAP-equivalent) is an established, IEEE/Scopus-recognized *separate category* from perturbation/Shapley methods (LIME, KernelSHAP) in the HAR literature, and is measurably cheaper — which is the real technical justification for SPARK's method choice, but this cost argument has not itself been made in a wearable-fall or local-gateway framing.**
- Evidence: The Kundu et al. 2026 survey formally separates "Gradient- and Path-Based Methods" (Saliency Maps, Integrated Gradients, Grad-CAM) from "Perturbation- and Sampling-Based Methods" (LIME, KernelSHAP, Anchors, PFI) as distinct algorithmic families in HAR, and cites gradient-based HAR work including Aquino et al. (gradient attribution on CNN embeddings for accelerometer HAR) and Lamaakal et al., "A tiny inertial transformer for human activity recognition via multimodal knowledge distillation and explainable ai," *Scientific Reports* 15(1):42335 (2025) — XTinyHAR uses Integrated Gradients + attention rollout on a lightweight inertial Transformer, the closest "tiny/embedded + gradient-based XAI + wearable IMU" match found, though it targets knowledge-distillation interpretability, not a deployed local-gateway clinical pipeline, and uses IG (path-integrated) rather than the simpler gradient×input SPARK implements.
- On the pure compute-cost side (not wearable-specific, but directly supports the engineering rationale): "Time to Focus" benchmark (arXiv:2202.03759) measured gradient-based methods (Saliency, IntegratedGradients, InputXGradient) as consistently the fastest attribution methods vs. KernelSHAP/ShapleyValueSampling, which were markedly slower on identical hardware. FastSHAP (arXiv:2107.07436) reports KernelSHAP taking 453–1090 minutes to explain 1,000 images vs. 0.3–1.0 min for gradient-based methods (GradCAM, IntGrad, SmoothGrad, DeepSHAP) — a 2–3 order-of-magnitude gap. A hardware-verification XAI paper (arXiv:2601.18696) reports gradient attribution at 0.16 ms/sample vs. SHAP (TreeExplainer) at 1.10 ms/sample on non-wearable data, a smaller but consistent margin.
- Confidence: Established (the taxonomic distinction and general cost ordering); Supported inference (that this cost gap is what justifies SPARK's specific choice — SPARK's own tracker doesn't cite this literature yet).
- Relevance to SPARK: This is the strongest available technical grounding for *why* gradient×input rather than KernelSHAP is the right choice for a real-time per-event gateway pipeline — but it is general-purpose evidence (mostly images/tabular data), not evidence from a wearable-fall-detection or local-gateway-specific study. It supports the engineering decision without yet supporting a novelty claim on its own.

**Finding 4: No source was found that frames explainability computation location as "separate local non-cloud gateway" (as opposed to on-wearable, cloud, or "the same device that also does sensing/inference") for wearable fall or HAR classifiers specifically.**
- Evidence: One non-indexed paper (Mohammed AlNusif, "Explainable AI in Edge Devices: A Lightweight Framework for Real-Time Decision Transparency," *International Journal of Engineering and Computer Science* (IJECS), Vol.14 Iss.7, July 2025) directly addresses SHAP/LIME/Saliency latency and memory trade-offs on Raspberry Pi/Jetson Nano/Coral TPU, including a fall-detection case study (TinyBERT text-classification of sensor summaries on Raspberry Pi + LIME, not gradient×input, not IMU-native). It explicitly frames "cloud-based vs. edge-based" XAI as the live research gap. — **Caveat: IJECS is not IEEE Xplore/Scopus/ACM-indexed and reads as lower-rigor (single author, self-described "cybersecurity masters student," non-standard citation format); treat as directional/corroborating only, not load-bearing evidence.**
- No stronger source (IEEE/Scopus) was found explicitly contrasting a wearable's own on-board compute, a separate local gateway device, and a cloud SHAP API as three distinct deployment points for fall/HAR explainability.
- Confidence: Unresolved — this may reflect a genuine literature gap (supporting SPARK's narrowed claim) or may reflect a search-term mismatch; recommend a follow-up formal database query using exact strings like "edge gateway" + "SHAP" + "wearable" directly against IEEE Xplore/ACM DL search interfaces (this pass used general web search reaching into indexed content, not direct database UI queries, so a small residual risk of missed hits remains).
- Relevance to SPARK: This is the crux of the narrowing argument — the "local non-cloud **gateway**" framing (as distinct from on-wearable or cloud) appears to be a genuinely under-addressed angle in the literature, which is what makes the narrowed claim defensible.

## task_2026-08-21_005

**Summary:** Track 4 — sensitivity-boosting literature for train_cnn.py: ranked additive techniques (focal loss, cost-sensitive threshold refinement, added augmentation, targeted hard-example reweighting; noted ensemble/snapshot approaches as higher-effort or out-of-scope) to help close the 87.81%→90% sensitivity gap without regressing specificity.

### Research question
Beyond the 5 techniques already implemented in `training/train_cnn.py` (v51: Youden's-J threshold tuning, class-balanced INT8 calibration sampling, time-series augmentation [temporal shift ±5 samples, magnitude scaling ±5%, Gaussian jitter], `class_weight="balanced"` + configurable `--pos-weight-boost` [default 1.25x], dropout/batch-norm regularization), what published techniques for imbalanced time-series/wearable classification could plausibly close the remaining ~2-point sensitivity gap (87.81%→≥90%, currently 0.9185 AUC-ROC) by Oct 31 2026, without regressing specificity below 90%?

### Bottom line
The literature most directly supports two low-effort, high-confidence additions on top of what's already implemented: (1) swapping or blending the current `class_weight`-based categorical cross-entropy with a **focal loss**, which has direct fall-detection precedent showing large sensitivity gains on imbalanced data without the dataset-level rebalancing SPARK already has; and (2) refining the existing Youden's-J threshold step into an explicit **cost-sensitive/asymmetric threshold selection** that weights missed falls more heavily than false alarms (J-statistic weights Se and Sp equally, which may not be the right operating point for a safety-critical minority class). Medium-effort additions — **time-warping/window-warping and mixup augmentation** (not currently in `augment_windows()`, which only does shift/scale/jitter) and **confusion-matrix-informed reweighting of specific hard ADL codes** (a domain-adapted, low-cost substitute for full hard-negative mining) — have supportive but less domain-direct evidence. Full multi-model ensembling has the strongest published sensitivity numbers on SisFall itself but changes the architecture/inference footprint and overlaps Track 5's scope; it is noted here only as a boundary flag, not recommended as a Track-4 (training-technique) action.

### Key findings

**Finding 1 — Focal loss shows large, fall-detection-specific sensitivity gains on imbalanced data.**
- Evidence: A wearable fall-detection transformer study reports a baseline model on imbalanced data achieving only 48.0% fall sensitivity; training the same class of model with a specialized focal loss on balanced data raised sensitivity to 90.5% (test) at 93.1% accuracy. A separate feasibility study customizes Lin et al.'s focal loss specifically to stop the loss being "overwhelmed" by the ADL majority class in a fall dataset.
- Source: "A Multi-Head Attention Transformer Model for Wearable in Situ Fall Detection" (PubMed 42376622); "Toward Real-Time, Robust Wearable Sensor Fall Detection Using Deep Learning Methods: A Feasibility Study" (MDPI Applied Sciences 13(8):4988, 2023).
- Confidence: Established (direct domain match: wearable fall detection, imbalanced classes, sensitivity as target metric) — but note these papers combine focal loss with dataset-level rebalancing/larger models too, so the isolated marginal effect of focal loss alone is not cleanly separable from their reports.
- Relevance to SPARK: `train_cnn.py` currently handles imbalance only via `class_weight="balanced"` × pos-weight-boost on standard categorical cross-entropy — this reweights the loss but doesn't down-weight easy majority-class examples the way focal loss's `(1-p)^γ` term does. Focal loss is a pure loss-function swap: no architecture change, no added inference cost, fully compatible with the locked TFLite-Micro-INT8 pipeline (loss only matters at training time). Concretely additive to v51's Technique 4 (positive-class boost) — could replace or be blended with it.

**Finding 2 — Explicit cost-sensitive threshold tuning outperforms symmetric threshold tuning on a real-world (not just lab) fall dataset.**
- Evidence: A recent framework tunes the decision threshold using a cost function that explicitly weights missed falls higher than false alarms (rather than Youden's J, which maximizes Se+Sp-1 with equal weight on both), achieving Recall=1.00, Precision=0.84, F1=0.91 on the FARSEEING real-world falls dataset (60+ hours of IMU data), with <5ms inference.
- Source: "Watch Your Step: A Cost-Sensitive Framework for Accelerometer-Based Fall Detection in Real-World Streaming Scenarios" (arXiv:2509.11789, 2025).
- Confidence: Established for the mechanism (cost-sensitive thresholding is a standard, well-validated technique) and Established that it outperformed a recall-only-focused baseline in this paper's own comparison; Supported inference that it would help SPARK specifically, since SPARK's current Youden's-J threshold is a symmetric compromise, not an asymmetric one reflecting "missed fall ≫ false alarm" cost.
- Relevance to SPARK: This is a direct, low-effort refinement of `find_optimal_threshold()` (v51 Technique 1) — replace the J-statistic objective with a cost-weighted objective (e.g., minimize `cost_FN × FN_rate + cost_FP × FP_rate` for a chosen cost ratio) computed on the same validation split, no retraining needed. Cheapest technique on this list to try since the infrastructure (threshold search over validation probabilities) already exists.

**Finding 3 — Time-warping/window-warping and mixup are validated time-series augmentations SPARK does not yet use.**
- Evidence: A comprehensive DA survey reports combined augmentation methods lifting a wearable-sensor classification baseline from 77.52% to 86.88%; a HAR-specific comparative study found time-warping "performs best to improve human activity recognition accuracy among other RT algorithms," while plain rotation/jittering alone was sometimes neutral or harmful; a separate multivariate TSC study found window-warp, cutmix, and mixup improve robustness "in a statistically significant way" across CNN/RNN/attention architectures on 26 UEA benchmark datasets; mixup is also specifically used in several wearable-HAR papers (e.g., "Attend and Discriminate," PAMAP2) as a regularizer for small-N wearable datasets.
- Source: "Data Augmentation for Time-Series Classification: a Comprehensive Survey" (arXiv:2310.10060); "A comprehensive survey and comparative analysis of time series data augmentation in medical wearable computing" (PLOS ONE, 2025, DOI 10.1371/journal.pone.0315343); "Robust Augmentation for Multivariate Time Series Classification" (arXiv:2201.11739); "Attend And Discriminate: Beyond the State-of-the-Art for HAR Using Wearable Sensors" (arXiv:2007.07172).
- Confidence: Established that these techniques help time-series/wearable classification generally; Supported inference for SPARK specifically, since no cited paper augments SisFall itself with time-warping/mixup — transferability from HAR/PAMAP2/UEA benchmarks to SisFall fall-vs-ADL is plausible but unconfirmed.
- Relevance to SPARK: `augment_windows()` (v51 Technique 3) currently does temporal shift, magnitude scaling, and jitter, but not time/window-warping or mixup — these are additive, not redundant. Caution: rotation-family augmentations were reported neutral-to-harmful in at least one wearable study (Um et al., cited in finding above), so any addition should be validated against the held-out test set before being kept, not assumed beneficial by default. Window-warping in particular changes fall-impact timing, which could interact with SPARK's `Δt < 300ms` Layer-1 gate timing assumptions if ever fed back into hardware-adjacent testing (it doesn't affect Layer-1 itself, since that's a separate rule-based gate, but worth flagging).

**Finding 4 — "Hard-negative mining" as commonly defined (object-detection/embedding literature) has no direct fall-detection precedent, but a domain-adapted analog (targeted reweighting of confusable ADL codes) is indirectly supported.**
- Evidence: Hard-negative/hard-example mining (OHEM) is a well-established technique in object detection and embedding/contrastive learning (its origin, Lin et al. 2017, is also focal loss's origin paper) but no fall-detection-specific paper in this search applies classic OHEM to accelerometer time series. However, one CNN-CausalLSTM fall-detection study reports that its only 3 misclassifications (out of 1444 SisFall test examples, 0 false negatives) came specifically from young-adult squat/crouch-after-jump activities — i.e., the errors concentrate in a small number of identifiable "hard" ADL types rather than being spread evenly.
- Source: "Fall Detection with CNN-Casual LSTM Network" (MDPI Information 12(10):403, 2021, DOI 10.3390/info12100403); OHEM/focal-loss background from "Focal loss for handling the issue of class imbalance" (Medium/Lin et al. 2017 lineage); Zilliz and Nextjournal explainers on hard-negative mining mechanics (general ML, not domain-specific).
- Confidence: Supported inference, not established — the mechanism (up-weighting or oversampling the specific SisFall activity codes/subjects that a first training pass misclassifies, rather than uniform class-weight boosting) is a reasonable transfer from the broader hard-example-mining literature, but it is not validated on SisFall or any fall dataset in the sources found.
- Relevance to SPARK: A lightweight, additive version of this doesn't require the OHEM machinery from object detection — it's an error-analysis loop: (1) train per v51 setup, (2) pull the confusion matrix by activity code (`F01–F15`/`D01–D19`) on the validation split, (3) identify which specific ADL codes account for disproportionate false positives / which fall codes account for false negatives, (4) oversample or further boost `class_weight` for just those codes in a second training pass. This is cheap to try since SPARK already has per-activity-code labels from `prepare_sisfall.py` and could be built as a small addition to the existing training script rather than a new pipeline.

**Finding 5 — Full ensemble/multi-branch architectures show the largest published SisFall gains, but are an architecture change, not a training-technique change — flagged as a Track 5 boundary item, not a Track 4 recommendation.**
- Evidence: A CNN+RNN ensemble architecture on SisFall reports mean accuracy 95%/96%/98% for Non-Fall/Pre-Fall/Fall; a CNN-BiLSTM with channel+temporal attention ensemble reports recall 95.67–97.96% and specificity 98.13–98.34% (not on SisFall specifically, cross-referenced from the same literature pass).

## task_2026-08-21_006

**Summary:** Track 5 complete: TFLite-Micro architecture alternatives researched (TCN, depthwise-separable, SE/attention) vs SPARK's 1D CNN. Recommendation: don't swap architecture before Oct 31 — literature shows 1-2pt gains at 2-75x SPARK's size; Track 4 training-level techniques are the better-leveraged investment.

### Research question
Do published lightweight TFLite-Micro-compatible architectures (TCN, depthwise-separable-conv variants, SE/attention blocks) at parameter budgets comparable to SPARK's 1D CNN (18.5KB INT8, ~9.3K params: Conv1D(32,k5)→MaxPool→Conv1D(64,k3)→GAP→Dense(32)→Dense(2)) report accuracy/sensitivity gains over plain 1D CNN on fall/HAR tasks, and is swapping architecture worth it before WP2's Oct 31 deadline (current: 87.81% sensitivity, 0.9185 AUC-ROC vs ≥90% target)?

### Bottom line
Published depthwise-separable and TCN architectures do exist at SPARK-adjacent scale and report sensitivity in the 96-99% range on SisFall — well above SPARK's current 87.81% — but the gain **attributable to architecture family alone**, holding scale roughly fixed, is modest (~0.3-2 points in controlled ablations). None of these results are apples-to-apples with SPARK's exact task/protocol (see Contradictions). SE/attention-block literature operates at 25-500x SPARK's parameter budget and doesn't transfer evidence at MCU scale. **Recommendation: do not swap CNN→TCN/depthwise-separable/SE before Oct 31; Track 4's training-level techniques are the better-leveraged use of remaining time.** If sensitivity is still short after Track 4 is exhausted, a MobileNet/ConvNeXt-style depthwise-separable block (36-74KB, proven on SisFall directly) is the lowest-risk architecture change to prototype post-deadline — not TCN (higher implementation complexity, smaller ablation-isolated gain) and not SE (no MCU-scale fall-detection evidence).

### Contradictions and limitations

- **Task/protocol mismatch, not just dataset match.** The strongest SisFall comparators (lwRPPC-TCN, MobileNet, ConvNeXt in the Pan et al. 2026 paper) solve **pre-impact fall prediction** (250ms lead time before impact, using peak-SMV-based impact labeling and a 0.75s window) via 5-fold cross-validation, not SPARK's **post-hoc binary FALL/NON_FALL classification** over a full 3s/200-sample window with subject-grouped 80/10/10 splitting. Different task, different windowing, different validation scheme. The reported sensitivity numbers are not a controlled measurement of "what SPARK's exact task would get with this architecture" — they establish that the architecture families are *capable* of high sensitivity on SisFall-sourced data, not that swapping SPARK's classifier head-for-head would reproduce these numbers.
- **No paper found that trains multiple architecture families on SPARK's exact task** (post-hoc binary classification, subject-grouped split, 200Hz/200-sample/6-channel raw input) to isolate architecture effect from task/protocol effect. This is the central gap in the evidence base for a direct swap decision.
- **SE/attention evidence gap is real, not just underexplored by this search** — every HAR+SE paper surveyed operates at ≥0.2M params; none report results at anywhere near SPARK's ~9K-param / 18.5KB tier. This is a genuine literature gap, not a search-coverage limitation (verified via WSense's own literature-survey table, Ige & Mohd Noor 2023, listing 10+ SE/attention HAR papers all >0.4M params).
- **TinyCNN's full architecture wasn't obtained** — only its parameter count, inference time, and headline sensitivity/specificity figures (via a citing paper and the original abstract), not layer-by-layer detail. If the team wants to pursue this specific reference, the primary paper (DOI:10.1016/j.bspc.2023.105325) needs a full read.
- **Sample-size/generalization caveat inherited from all comparators**: SisFall itself has known dataset-specific quirks (only one elderly subject, SE06, performed actual falls — noted independently in the WTCN paper's methodology) that could inflate any model's apparent sensitivity on SisFall specifically, including SPARK's own 87.81% figure and all comparators cited here. This is a pre-existing SisFall limitation, not new to this track, but it means none of the cross-paper sensitivity comparisons should be read as precise.

### Recommendation

1. **Do not swap SPARK's CNN architecture before the Oct 31 WP2 deadline.** The controlled ablation evidence (Pan et al. 2026, Table 5) shows architecture-family choice alone (TCN vs. depthwise-separable vs. plain conv) buys on the order of a few tenths of a percentage point in sensitivity when parameter scale is held roughly fixed — small relative to SPARK's ~2.2-point gap (87.81%→90% target) and not worth the implementation/validation risk against a hard deadline.
2. **Prioritize Track 4's training-level techniques** (the parent task explicitly poses this as the alternative investment) — SPARK's v51 changelog shows 5 such techniques already implemented (threshold tuning, class-balanced calibration, augmentation, pos-weight boost, dropout/BN), so the marginal next step is likely tuning their hyperparameters (e.g., `--pos-weight-boost` beyond the default 1.25x) rather than architecture work.
3. **If the sensitivity gap persists after Track 4 is exhausted**, the lowest-risk architecture change to prototype (post-deadline) is a MobileNet/ConvNeXt-style depthwise-separable conv block, sized to land in the 36-74KB range — this is the only architecture family in this survey with direct, same-dataset (SisFall), same-metric precedent at a size that still fits SPARK's 120KB ceiling with large margin. Avoid SE/attention blocks specifically until closer literature at SPARK's true scale exists; avoid a full custom TCN+reparameterization stack (lwRPPC-style) unless the team has bandwidth matching the original paper's engineering effort, since the ablation shows most of its benefit comes from the depthwise-separable block, not the TCN stage.
4. **Flag TinyCNN (DOI:10.1016/j.bspc.2023.105325) for a full read** as the most aggressive size-matched precedent (546 params, Cortex-M4-class MCU proven, same primary dataset) if/when the team revisits architecture post-deadline.

## task_2026-08-21_007

**Summary:** Track 6 research memo: partial-freeze fine-tuning + SisFall/Nepal-cohort data-mixing is the best-supported strategy for Action #23; Reptile few-shot is a fallback only, capped well below WP2's 90/90 target. 6 findings, IEEE/Sensors/Springer/arXiv sources, full checkpoint in result_text.

### Research question
Given SPARK's pattern of pretraining on SisFall (38 subjects) then planning to fine-tune on a small self-collected Nepali cohort (§2.4, §5, Action #23, count TBD): what does the domain-adaptation / transfer-learning / few-shot-calibration literature recommend for exactly this large-public-benchmark → small-local-cohort pattern in wearable sensor classification — including known failure modes (catastrophic forgetting, overfitting on the small set) and mitigations (partial-freeze fine-tuning, learning-rate schedules, data-mixing ratios between SisFall and new data)?

### Bottom line
The best-supported concrete strategy is: (1) freeze train_cnn.py's early convolutional layers and retrain only the later conv block + dense head on the Nepal cohort (partial-freeze fine-tuning), and (2) do not fine-tune on the Nepal cohort alone — mix SisFall windows into the fine-tuning batches (rehearsal/data-mixing), which is directly evidenced by an IEEE-Xplore paper doing exactly this SisFall+self-collected combination for wearable fall detection. Reptile-style few-shot meta-learning is a documented fallback but tops out well below SPARK's ≥90%/≥90% WP2 gate, so it should not be the primary plan unless Action #23's subject count ends up genuinely tiny.

### Key findings

**Finding 1 — The domain gap SPARK is worried about is documented in SisFall's own source paper, not just inferred.**
- Evidence: SisFall's original paper trained fall/ADL detection thresholds on young adults and validated on independent elderly subjects; sensitivity dropped for most tested features on the elderly group. The authors attribute this to elderly participants falling with lower accelerations and instinctively cushioning impacts, unlike young adults' faster, uncushioned simulated falls. Re-training the same features using only elderly data recovered much of the lost performance, confirming the shift traces to training-population mismatch rather than the features themselves.
- Source: Sucerquia, López, Vargas-Bonilla, "SisFall: A Fall and Movement Dataset," Sensors 17(1):198 (2017).
- Confidence: Established.
- Relevance to SPARK: Direct evidence (from the dataset SPARK already trains on) that a SisFall-only model is expected to under-detect real Nepal-cohort falls without adaptation — strengthens the case that Action #23 is not optional polish but a real accuracy requirement.

**Finding 2 — Partial-freeze fine-tuning (freeze early layers, retrain only dense/head layers) beats training-from-scratch on small wearable accelerometer target sets.**
- Evidence: Maray et al. trained an LSTM fall-detector on a larger wrist-worn accelerometer source dataset (528 falls/14 subjects), then adapted it to two much smaller target datasets (202 falls/8 subjects; 144 falls/12 subjects) by freezing early layers and retraining only the dense layers. Across 70/30 and leave-one-subject-out splits this beat training-from-scratch by F1 +7% to +14% and AUC +0.15 on average, with fewer false positives in every reported experiment.
- Source: Maray, Ngu, Ni, Debnath, Wang, "Transfer Learning on Small Datasets for Improved Fall Detection," Sensors 23(3):1105 (2023), doi:10.3390/s23031105 (open access, CC-BY).
- Confidence: Established.
- Relevance to SPARK: Closest direct analogue to Track 6's scenario (wrist-worn accelerometer, binary fall/non-fall, small target cohort). Gives a concrete recipe: freeze train_cnn.py's convolutional feature-extraction layers, retrain only the final dense/classification head on the Nepal cohort.

**Finding 3 — An independent replication of the same partial-freeze pattern (retrain only fully-connected layers) on IMU HAR converges fast and reaches high accuracy.**
- Evidence: A CNN pretrained on large virtual-IMU data, then fine-tuned only on its fully-connected layers using a much smaller real-IMU dataset, converged in a few iterations and reached 91.15% accuracy on the real-IMU target set.
- Source: "A Deep Learning Method for Complex Human Activity Recognition Using Virtual Wearable Sensors," arXiv:2003.01874.
- Confidence: Established for that dataset/task; Supported inference for direct transfer to SisFall→Nepal-cohort (different domain gap: virtual-vs-real, not SisFall-vs-Nepal).
- Relevance to SPARK: A second, independent line of evidence for the same partial-freeze strategy — increases confidence this is a sound default, not a one-paper artifact.

**Finding 4 — Mixing the small target dataset with the original large source dataset (rather than fine-tuning on the small set alone) directly improved accuracy in a SisFall+self-collected wearable fall-detection setup.**
- Evidence: An IEEE Sensors Journal paper trained a model on a self-collected wearable dataset alone (98.05% accuracy, with concerning false negatives), then retrained on a combined SisFall + self-collected dataset, raising accuracy to 99.38% with fewer missed falls.
- Source: Campanella, Alnasef, Falaschetti, Belli, Pierleoni, Palma, "A Novel Embedded Deep Learning Wearable Sensor for Fall Detection," IEEE Sensors Journal, vol. 24, pp. 15219–15229 (2024), doi:10.1109/JSEN.2024.3375603. IEEE Xplore-indexed.
- Confidence: Established.
- Relevance to SPARK: The single strongest, most directly transferable finding for Track 6 — it is literally the SisFall+self-collected-wearable-dataset combination SPARK plans. Directly answers the "data-mixing ratios between SisFall and new data" part of the task spec: mix, don't replace. (Exact mixing ratio wasn't recoverable from the accessible portions of this paper this session — flagged below as an open follow-up.)

**Finding 5 — For genuinely few-shot regimes, Reptile-based meta-learning transfer gives a measurable but limited boost, well short of SPARK's target.**
- Evidence: A deep HAR model pretrained on a large public dataset, then adapted via the Reptile meta-learning algorithm for 3-way, 5-shot classification, reached 74.86% (new activities, same user) and 79.20% (same activities, new user) average accuracy — about 10 percentage points better than few-shot learning without pretrained-parameter transfer, but still well below 90%.
- Source: Ganesha, Gupta, Gupta, Rajan, "Few-shot transfer learning for wearable IMU-based human activity recognition," Neural Computing and Applications 36:10811–10823 (2024), doi:10.1007/s00521-024-09645-7.
- Confidence: Established for that benchmark; Supported inference for whether it generalizes to SPARK's binary fall/non-fall task at higher per-class counts.
- Relevance to SPARK: Sets a ceiling — if Action #23 lands at true few-shot scale, meta-learning alone is unlikely to hit the WP2 ≥90%/≥90% gate. Strengthens the case (cross-ref Track 9) for a Nepal-cohort subject count large enough to support Findings 2/4's regime rather than Finding 5's.

**Finding 6 — Catastrophic forgetting during fine-tuning is a well-documented general risk with converging, complementary mitigations.**
- Evidence: A recent transfer-learning survey states that fine-tuning-induced catastrophic forgetting degrades generalizable pretrained features, and that small learning rates or layer-freezing help — with a caveat that overly aggressive freezing/small-LR risks trapping the model in local minima when the pretrain-to-target gap is large. The same literature describes layer-wise ("discriminative") learning rates combined with gradual unfreezing (the ULMFiT pattern) as an established way to protect early general-purpose features while adapting later task-specific ones. Separately, established regularization methods (L2-SP; DELTA) explicitly penalize parameter drift from pretrained weights to prevent forgetting.
- Source: "Understanding Knowledge Transferability for Transfer Learning: A Survey," arXiv:2507.03175; discriminative fine-tuning + gradual unfreezing as replicated in a FinBERT study, arXiv:1908.10063; L2-SP/DELTA as summarized in "Catastrophic Forgetting Meets Negative Transfer: Batch Spectral Shrinkage for Safe Transfer Learning" (NeurIPS).
- Confidence: Established as general deep-learning principles; Supported inference (not directly tested) that they transfer unmodified to a small 1D CNN on 200×6 IMU windows — none of these sources use wearable IMU/fall data.
- Relevance to SPARK: Concrete dials for whoever implements Action #23, layered on Findings 2/4: freeze/low-LR the early conv layers, unfreeze progressively if forgetting appears, always keep SisFall data in fine-tuning batches (echoes Finding 4), and track SisFall held-out Sensitivity/Specificity throughout fine-tuning (not just Nepal-cohort metrics) as a forgetting tripwire.

### Research question
Does recruiting healthy adults 18-35 to perform *simulated* falls (per DATA_COLLECTION_PROTOCOL.md §2.2/§4) adequately proxy real fall kinematics for SPARK's actual target population (healthy independent elderly, per tracker §0/§2.7/Action #34 rationale)? What protocol adjustments have comparable published studies used to partially compensate?

### Bottom line
No — young-adult simulated falls are a well-documented, systematically biased proxy for elderly fall kinematics, and this is not a SPARK-specific problem but a field-wide, decades-old methodological compromise that the fall-detection literature (including SisFall's own authors) explicitly flags. The bias direction is consistent and predictable: young-adult simulated falls have higher acceleration/jerk and less protective/cushioning behavior than real elderly falls, which pushes trained thresholds and classifiers toward under-sensitivity on the real elderly population — directly relevant to WP2's sensitivity gap. Partial, literature-backed compensations exist (adjusted fall-elicitation instructions; supplementing with real-elderly ADL-only data; explicit limitation framing) but no published method fully closes the gap; real-world elderly fall data remains the only complete solution, and that is infeasible for SPARK's timeline/ethics scope.

### Key findings

- **Finding:** SisFall's own authors (already the primary source in SPARK's notebook) found that elderly-performed ADLs/falls have significantly smaller acceleration amplitude than young-adult-performed ones, and that young adults simulating falls "fall faster... without trying to avoid the impact," while their one elderly fall-participant (a 60-year-old Judo expert) consistently tried to cushion/soften every fall — a natural protective reflex absent in young-adult simulation.
- **Evidence:** Direct comparison across 38 subjects (23 young adults 19-30, 15 elderly 60-75, one elderly fall-simulator); algorithms trained on young-adult data and validated on the elderly participant showed sensitivity drops from ~92-98% (young-on-young) to ~62-88% (young-trained, elderly-tested) depending on feature (Table 5 of the paper); retraining on elderly data still underperformed young-on-young accuracy, indicating a genuine signal-distribution shift, not just a threshold-shift artifact.
- **Source:** Sucerquia, López & Vargas-Bonilla, "SisFall: A Fall and Movement Dataset," *Sensors* 17(1):198 (2017), doi:10.3390/s17010198.
- **Confidence:** Established (primary source, peer-reviewed, already validated in-notebook).
- **Relevance to SPARK:** This is the exact dataset SPARK trains on. Confirms the mechanism (amplitude/threshold bias) that Track 8 was asked to assess is real and already latent inside SPARK's *existing* primary dataset, not just a hypothetical risk from the new Nepal-cohort protocol.

- **Finding:** Independently of SisFall, a purpose-built comparison of real vs. simulated backward falls found real-world falls by older people (mean age 68.8) show significantly more acceleration variation and higher maximum jerk than falls self-initiated by young students instructed to "fall like a frail old person" — but when young subjects were instead released suddenly from a backward lean and told to try to avoid falling (an externally-triggered, non-self-initiated protocol), the resulting acceleration/jerk values were *closer* to real elderly falls than the self-initiated "act frail" version.
- **Evidence:** 5 real-world falls (4 subjects) vs. simulated falls by 18 healthy students, two experimental protocols directly contrasted.
- **Source:** Klenk et al., "Comparison of acceleration signals of simulated and real-world backward falls," *Med Eng Phys* 33(3):368-373 (2011), doi:10.1016/j.medengphy.2010.11.003; mechanism further explained in Sczuka et al., "Re-Enactment as a Method to Reproduce Real-World Fall Events," *JMIR* (2020), doi:10.2196/13961.
- **Confidence:** Established for the specific finding (peer-reviewed, small-N but purpose-designed comparison); the generalizability of "lean-and-release beats self-initiated" beyond backward falls specifically is a supported inference.
- **Relevance to SPARK:** Gives a concrete, low-cost protocol adjustment: for SPARK's F01-F08 fall types, prefer eliciting falls via an external trigger/unexpected release (where safely possible for the given fall mechanism, e.g. F03 backward slip, F08 standing-up collapse) with instructions to try to recover, rather than a fully self-directed "perform a fall" instruction — likely to produce kinematics closer to real elderly falls than the protocol's current wording ("simulate tripping," "simulate sudden loss of consciousness," etc., which reads as self-initiated/deliberate).

- **Finding:** Algorithms tuned and validated on simulated (mostly young-adult) falls report far better performance than the same class of algorithm tested on real-world falls: a systematic benchmark of 13 published fall-detection algorithms against 29 real-world falls from high-fall-risk patients found average sensitivity of only 57.0%±27.3% (max 82.8%) and specificity 83.0%±30.3%, compared to the ~91% sensitivity / ~99% specificity typically reported when the same class of algorithms is validated only on simulated data.
- **Evidence:** 29 real-world falls (SensAction-AAL/FARSEEING repository) vs. published simulated-fall benchmarks, meta-comparison across 13 algorithms.
- **Source:** Bagalà et al., "Evaluation of accelerometer-based fall detection algorithms on real-world falls," *PLoS One* 7(5):e37062 (2012), doi:10.1371/journal.pone.0037062; sensitivity/specificity contrast figures corroborated in Broadley, Klenk, Thies, Kenney & Granat, "Methods for the Real-World Evaluation of Fall Detection Technology: A Scoping Review," *Sensors* 18(7):2060 (2018), doi:10.3390/s18072060.
- **Confidence:** Established (peer-reviewed, real-world outcome data, cross-corroborated by an independent scoping review of 22 studies).
- **Relevance to SPARK:** Bagalà also found the failures concentrate in *low-impact* falls (falling onto a bed/sofa, during transfers) — a pattern likely under-represented in SPARK's own simulated fall list (all onto a 30cm crash mat; none from a chair/bed transfer failure at low height). This compounds the age-proxy problem with a mechanism-coverage gap: SPARK's F04 ("fall while sitting") is the closest analog but still simulated onto the same crash mat rather than a genuinely low-height/soft-surface transfer failure.

- **Finding:** SPARK's own compromise — recruiting only young, healthy volunteers for both fall *and* ADL data, with no elderly subjects in the local collection at all — is more extreme than several comparable published protocols, which instead used a *mixed* design: young volunteers for the (unsafe-for-elderly) fall simulations, but real elderly volunteers for the ADL/non-fall class, which carries no comparable safety risk.
- **Evidence:** SisFall itself: 15 real elderly subjects performed 15 ADL types (no falls, per physician recommendation) alongside 23 young adults who performed both ADLs and falls. Bourke et al.'s waist-accelerometer study used 10 young volunteers for 240 simulated falls/120 ADL plus 10 *real* elderly volunteers for 240 scripted ADL and 52.4 hours of continuous unscripted normal ADL. Liu & Cheng's SVM fall-detector study used 20 young volunteers for scripted activities plus 5 real elderly volunteers, with continuous unscripted testing on both groups.
- **Source:** Sucerquia et al. 2017 (as above); Bourke et al., "Evaluation of waist-mounted tri-axial accelerometer based fall-detection algorithms during scripted and continuous unscripted activities," *J Biomech* 43(15):3051-3057 (2010); Liu & Cheng, "Fall Detection with the Support Vector Machine during Scripted and Continuous Unscripted Activities," *Sensors* 12(9):12301-12315 (2012), doi:10.3390/s120912301.
- **Confidence:** Established (three independent, peer-reviewed precedents using the same mixed-cohort structure).
- **Relevance to SPARK:** This is the single most actionable, low-risk adjustment available to Action #23. SPARK's own protocol document already excludes falls for anyone with balance/cardiovascular/injury risk factors (§2.2 exclusion criteria) — the same reasoning that led SisFall/Bourke/Liu to exclude elderly from the *fall* block specifically, while still including them in the *ADL* block. Recruiting even a handful of real elderly volunteers (e.g. KEC staff family members, retired faculty — mirroring SisFall's own "retired employees/parents of employees" recruitment) for ADL-only data (D01-D14, no fall trials) would give SPARK a genuine elderly-kinematics anchor for the *specificity* side of the classifier and for validating whether ADL-based Layer-1 threshold false-positive behavior transfers to real elderly movement patterns, without adding any new physical risk beyond what's already in the protocol for the D-block.

- **Finding:** The same young-adult-as-elderly-proxy compromise SPARK is making is widespread and even present in a highly-cited, purpose-built "elderly" pre-impact fall dataset — indicating this is accepted (if criticized) field practice, not a departure from norms.
- **Evidence:** KFall — explicitly titled "...for Detecting Pre-impact Fall of the Elderly" — was collected entirely from 32 healthy young Korean men (mean age 24.9±3.7) performing simulated falls and ADLs; no elderly subjects at all.
- **Source:** Yu, Jang & Xiong, "A Large-Scale Open Motion Dataset (KFall)...," *Front Aging Neurosci* 13:692865 (2021), doi:10.3389/fnagi.2021.692865 (100+ citations per PMC record).
- **Confidence:** Established (primary source, dataset demographics directly reported).
- **Relevance to SPARK:** Useful for thesis framing — SPARK is not introducing a novel weakness by using a young cohort; it can cite this as evidence the compromise is standard, while still being candid (per Bagalà/Broadley/Klenk above) that the compromise has a real, measured cost in sensitivity that the thesis limitations section should not understate.

### Contradictions and limitations
- No contradiction among sources — all point the same direction (young-adult simulation over-estimates fall severity/speed relative to real elderly falls) and all are corroborating rather than conflicting.
- Sample sizes throughout this literature are small by nature of the phenomenon (Klenk: 5 real falls; Bagalà: 29 real falls) — this is a known, field-wide constraint (Bagalà estimates ~300 person-years of continuous monitoring would be needed to passively capture 100 real falls), not a weakness specific to any one study; SPARK cannot realistically obtain real elderly fall data within its timeline, which is why every mitigation here is a partial compensation, not a fix.
- All quantitative kinematic/sensitivity comparisons found (SisFall, Klenk, Bagalà, KFall) come from European, North American, or Korean cohorts. No literature was found specifically characterizing Nepali/South Asian elderly fall kinematics or whether this population's fall dynamics track the reviewed literature — this is a genuine unresolved gap, distinct from (but adjacent to) Track 3's Claim-2 novelty check on the dataset's Nepal-context framing; flagged here for cross-reference, not re-litigated.
- The Klenk "lean-and-release" finding is from a single small study on backward falls specifically; whether the same instruction-based improvement generalizes to forward falls, lateral falls, or syncope-type collapse (SPARK's F01, F05/F06, F07) is a supported inference, not directly demonstrated in the literature reviewed.

### Recommendation
1. **Protocol wording (Action #23, lowest-cost change):** For fall types where it is safe to do so (e.g. F03 backward slip, F08 standing-up collapse), reword execution instructions from purely self-initiated ("simulate X, fall onto mat") toward an externally-cued or recovery-attempt framing consistent with Klenk et al.'s finding that this produces kinematics closer to real elderly falls — while keeping the existing crash-mat/spotter safety apparatus unchanged.
2. **Add a small real-elderly ADL-only sub-cohort** (no fall trials), following SisFall/Bourke/Liu's own precedent and consistent with SPARK's own exclusion-criteria logic (elderly excluded from falls, not from ADLs) — even 3-5 KEC-affiliated retired staff or faculty family members, physician-screened as SisFall did, would give SPARK a genuine elderly-kinematics anchor for specificity validation and Layer-1 false-positive checking. This is a scope addition for whoever finalizes Action #23's HOD-pending protocol, not a change SPARK's tracker or code should adopt unilaterally.
3. **Validate Layer-1 threshold tuning (open legacy Action #7) against SisFall's real elderly subgroup specifically** — held out during subject-grouped CV as its own validation slice — rather than only against the young Nepal cohort, since SisFall already contains genuine elderly-kinematics ground truth that is currently at risk of being diluted into the general training pool.
4. **Thesis language (Ch.5/limitations):** State explicitly, with citations to Sucerquia et al. 2017 and Klenk et al. 2011, that young-adult simulated falls systematically overestimate acceleration/jerk relative to real elderly falls, that this is standard (if imperfect) field practice (cite KFall as a comparable precedent), and that SPARK's reported sensitivity/specificity figures should be read as an upper bound relative to true elderly-population performance until validated against real elderly data.
5. Flag findings 1-3 for whoever owns Action #7 (Layer-1 tuning) and Track 6 (fine-tuning strategy) since they affect the same underlying data-population-mismatch risk from a different angle than Track 6's SisFall→Nepal-cohort fine-tuning question.

## task_2026-08-21_011

**Summary:** TRACK 10 complete. TPU 95A rigid-plastic boss ratios don't transfer directly — TPU-specific practitioner guidance calls for flat 3–4mm wall (not a 2–2.5x-diameter multiplier), and TPU is independently documented to strip self-tapping threads easily. Delivered concrete boss spec (pilot hole ~2.0–2.1mm, OD ~8–10mm, blind standoff ~7–8mm deep) plus a flagged Action #39 fastener-choice risk (embedded nut / heat-set insert may outperform self-tapping in TPU 95A) and an Action #17 geometry-interference risk (boss depth vs. Zone 1's ~7mm total wrist-zone thickness).

### Research question
What minimum boss wall-thickness / outer-diameter design guidance (as a function of M2.5 screw diameter) applies to self-tapping fasteners in flexible TPU 95A, specifically for SPARK's FDM-printed enclosure — and does the enclosure's existing 2mm nominal wall spec (CAD_SOFTWARE_GUIDE.md / DI-01) satisfy it?

### Bottom line
No — the 2mm nominal shell wall is a general enclosure-wall spec, not a boss spec, and is well short of what's needed. Two independent, convergent bodies of evidence say so: (1) published injection-molding boss guidance (7+ manufacturer/mold-design sources) converges on boss OD = 2.0–2.5× screw major diameter with boss wall ≤60% of *nominal* wall — but that 60% ceiling is an injection-molding sink-mark rule that does not apply to FDM and, if naively applied to SPARK's 2mm wall, would suggest an ~1.2mm boss wall, which is backwards for FDM/TPU. (2) TPU/FDM-specific practitioner guidance instead gives a flat minimum: 3–4mm wall around a structural screw boss in TPU (not a diameter multiplier), and separately documents that TPU generally holds self-tapping threads poorly (screws strip out) — heat-set inserts work in 95A+ TPU but pull out in softer grades. Applying the TPU-appropriate rule to SPARK's M2.5×8mm sourced fastener (Action #39) yields a concrete boss spec: ~2.0–2.1mm pilot hole, ~8–10mm boss OD, ~7–8mm deep blind standoff — a feature the enclosure's current geometry/cost estimate (v38, NPR ~90, 18.5cm³) does not budget for at all, and which may not physically fit inside Zone 1 (wrist zone, ~7mm total exterior thickness per DI-02).

### Key findings

**Finding 1 — Standard (rigid-plastic/injection-molding) boss sizing ratios**
- **Evidence:** Boss outer diameter should be 2.0–2.5× the screw's major diameter; boss wall thickness should be ≤60% of the part's nominal wall to avoid sink marks, but can be increased in non-visible areas specifically to handle self-tapping screw stress; pilot hole ≈ 0.7–0.85× screw major diameter (Toray/Torelina gives 85% specifically, with 50–70% thread engagement).
- **Source:** Converging across 7 independent manufacturer/mold-design guides (Walsh's Plastic Consulting; RapidDirect; SWCPU (2×); Zhongde; Sositar; JCFasteners/Plastite; Toray Torelina engineering-plastics design guide).
- **Confidence:** Established (independently corroborated numeric ratios).
- **Relevance to SPARK:** Baseline formula, but calibrated for *injection-molded rigid engineering thermoplastics* (ABS/PC/nylon/PPS), not TPU or FDM — the task explicitly flags this transfer as unsafe, and the evidence confirms why (next finding).

**Finding 2 — The "60%-of-nominal-wall" boss rule is an injection-molding sink-mark rule, not a strength rule, and doesn't apply to FDM**
- **Evidence:** Every source stating the 60% ceiling ties it explicitly to sink-mark/void avoidance during injection-molding cooling — a process artifact of molten-material shrinkage around a core pin, which has no FDM analogue (FDM has no core pin, no molding sink marks in this sense).
- **Source:** Same 7 boss-design guides as Finding 1.
- **Confidence:** Established.
- **Relevance to SPARK:** If SPARK's CAD design (Sankalpa) naively applied the 60% rule to the existing 2mm wall (→ ~1.2mm boss wall), that would be actively wrong — undersized for FDM/TPU in the opposite direction from what's actually needed. This is the single most important caveat for whoever builds the CAD model.

**Finding 3 — FDM-specific (rigid-material) boss guidance is already thicker than injection-molding ratios**
- **Evidence:** Protolabs/Hubs: minimum wall around a threaded hole ≈ 1× the fastener's nominal diameter (e.g., M5 → 5mm wall). SelfCAD: boss/nut wall 3–4mm with 2–3 perimeters. Sovol (heat-set insert guide): 4–6 perimeters recommended around a screw-boss feature for durability; explicitly notes thread-forming (self-tapping) screws strip the bore on repeated removal in FDM parts; FDM is anisotropic (weaker layer-to-layer bond) so pull-out/shear/bend all load the boss differently — print a test coupon in the actual orientation before committing.
- **Source:** Protolabs Network/Hubs enclosure-design guide; SelfCAD threads-and-screws guide; Sovol heat-set-insert guide (all FDM-specific, non-peer-reviewed practitioner/vendor sources).
- **Confidence:** Established (3 independent FDM-specific sources, consistent with each other).
- **Relevance to SPARK:** Confirms FDM in general already needs more wall than injection-molding ratios suggest — before even accounting for TPU's added softness.

**Finding 4 — TPU-specific structural boss guidance (flat minimum, not a diameter multiplier) and documented poor thread-holding**
- **Evidence:** For TPU 95A specifically: "A 2mm wall in 95A TPU is floppy. For structural FPV mounts, minimum 3mm walls, 4mm in high-stress areas (camera cage arms, **screw bosses**)." Separately: "TPU holds threads poorly — screws strip out easily," with the guide's own recommended mitigation being embedded hex nuts or through-bolts with a lock nut rather than direct self-tapping, or heat-set inserts — which "work in 95A+ TPU but pull out under load in softer grades" (95A is the firm end of the TPU range, so SPARK's chosen grade is the more favorable case, but still flagged as thread-strip-prone for direct self-tapping).
- **Source:** UAVMODEL Insights "TPU 3D Printing Guide... FPV Part Design" (2026), a detailed FPV/drone-part practitioner guide with FDM-TPU-specific design tables; single source (not independently cross-verified by a second TPU-specific source in this search pass).
- **Confidence:** Established from one detailed, internally consistent, recent source; **not independently corroborated** — treat the exact "3–4mm" figure as a strong starting point, not a validated constant, until confirmed against a test print.
- **Relevance to SPARK:** Directly answers the research question — the applicable wall figure is a flat ~3–4mm around the boss (not the 2–2.5× diameter multiplier from rigid-plastic guidance, and not the 60%-of-nominal-wall figure either). Also directly implicates **Action #39** (fastener choice, not just #17's boss geometry): if SPARK's locked M2.5 self-tapping screws prove to strip in practice, the sourced fallback (embedded nut / heat-set insert) is already documented as TPU-95A-compatible and worth keeping as a documented contingency, even though the task scope here is boss dimensions, not re-opening the fastener decision.

**Finding 5 — Boss must be a deep blind standoff, not just a thickened flat wall — this is what actually prevents "bottoming through toward skin"**
- **Evidence:** Blind-hole/tapped-hole practice (general fastening engineering) calls for a hole depth beyond the minimum usable thread length, with clearance at the bottom for chips/tolerance — i.e., a blind standoff, not a flush-drilled through-wall. Toray Torelina's pull-out-strength model shows pull-out strength keeps rising with effective engagement depth up to the point the screw's own tensile strength becomes the limiting factor (for M3 in their material, ≥6mm effective depth exceeded the screw's own fracture load) — i.e., there's a real depth below which pull-out strength is depth-limited, not screw-limited.
- **Source:** Practical Machinist forum (general machining/fastening practice); Toray Torelina design guide §10 (engineering-plastics screw fastening, with worked pull-out-strength formula).
- **Confidence:** Established for the general principle (blind hole ≠ flush drilled wall); the specific ≥6mm-for-M3 pull-out crossover is Torelina-material-specific (glass-filled PPS, not TPU) so its numeric value doesn't transfer, only the *qualitative* depth-vs-strength relationship does — flagged as Supported inference when applied to TPU.
- **Relevance to SPARK:** This directly resolves the "screw bottoming through the inner wall toward skin" concern named in the task. That failure mode only happens if the screw is driven into a flat, non-bossed 2mm wall — an 8mm screw would then travel ~6mm past a 2mm wall with nowhere for the thread to seat, either stripping out or punching through toward the skin-facing surface. The fix is not a thicker uniform shell wall (which would blow the mass/cost budget across the whole part) but a **local blind-boss standoff**, closed on the skin-facing side, deep enough to contain the screw's usable thread engagement (recommend ~6–7mm of engageable pilot bore for an 8mm screw, plus ≥0.5–1mm solid material at the bottom of the blind hole) while remaining closed against the exterior skin-facing wall.

**Finding 6 — Boss geometry may not physically fit in Zone 1 (wrist zone) at the size this evidence recommends**
- **Evidence (from repo, not external literature):** DI-02 (`DESIGN_IDEAS.md`, canonical concept) specifies Zone 1 (wrist) as housing only the MPU6050 IMU (~15×20×3mm) with a "ultra-slim wrist clearance," implying a thin total cross-section; Zone 2 (forearm) houses the ESP32-S3 (~7mm), 1000mAh LiPo (~7mm), TP4056 (~2mm) and is explicitly the "elevated electronics chamber." A ~7–8mm-deep boss standoff (Finding 5) protruding from a 2mm inner wall would consume most or all of Zone 1's available internal depth, and in Zone 2 would compete directly with the already-tight 7mm component stack.
- **Source:** SPARK repo, `dev_logs/design-assets/DESIGN_IDEAS.md` (DI-01/DI-02), cross-checked against `dev_logs/SPARK_TRACKER.md` §1 Action #39 (fastener geometry) and CAD_SOFTWARE_GUIDE.md (2mm wall spec) — internal, not external, evidence.
- **Confidence:** Supported inference (component footprint dimensions are stated in the repo as approximate/pre-CAD; no actual enclosure cross-section exists yet to confirm interference).

Sankalpa should treat boss placement, not just boss dimension, as a CAD constraint to solve before finalizing DI-02 into a real model.

## task_2026-08-21_012

**Summary:** MPU6050 wake-on-motion is real, documented, and compatible with the locked Layer 1 gate — but only saves meaningful power if paired with ESP32-S3 light-sleep, since the MPU6050 itself is a small fraction of the 110–140mA R-05 budget. FallGuard driver comparison is moot: no FallGuard source exists in-repo to diff against. Recommend esp-idf-lib's native ESP-IDF mpu6050 component (raw-register, no DMP) over an i2cdevlib/DMP port.

### Research question
(a) Is MPU6050's low-power/interrupt-driven wake-on-motion mode compatible with SPARK's Layer 1 gate design (§2.5) without breaking the 200Hz continuous-sampling assumption the gate's threshold math depends on? (b) What does FallGuard's legacy MPU6050 driver pattern vs. current best-practice I2C/DMP access imply for Action #24's reuse-vs-rewrite decision?

### Bottom line
(a) **Compatible, with a specific two-tier design** — MPU6050's built-in Motion Detection Interrupt + Low-Power Accelerometer (cycle) mode can gate the ESP32-S3 into light-sleep during genuine stillness, waking it (in <1ms) back into full 200Hz continuous sampling before gate.cpp's existing 2.5g/300ms logic ever needs to run — no change to the locked thresholds required. But the MPU6050 itself only draws ~3.7–3.9mA active vs. ~10–110µA in low-power cycle mode, which is a small slice of the ~110–140mA total system draw R-05 already cites (dominated by ESP32-S3 CPU+BLE). **The real power lever is the ESP32-S3 host entering light-sleep, gated by the MPU6050 interrupt — not the MPU6050's own mode alone.** R-05's existing mitigation text ("sleep modes between windows") already gestures at this but has never been specified; this closes that gap.

(b) **The reuse-vs-rewrite question is moot as framed** — no FallGuard driver source exists anywhere in the current SPARK repo to reuse or diff against (confirmed by inspecting `firmware/main/drivers/mpu6050.h/.cpp`, whose own header comments state this explicitly). The real decision is which *external* pattern to build the from-scratch driver on: an i2cdevlib/DMP-style port (Arduino-era, has a documented history of ESP-IDF version-compatibility breakage) vs. a native ESP-IDF raw-register driver in the esp-idf-lib style (already what SPARK's current stub is shaped like). Recommend the latter.

### Key findings

**Finding 1: MPU6050's Motion Detection Interrupt + Low-Power Accelerometer mode is a real, documented, independently-used mechanism for exactly this use case.**
- Evidence: InvenSense's own MPU-6000/MPU-6050 Product Specification documents a "Low power accelerometer mode" with four selectable wake frequencies and current draws: 10µA @1.25Hz, 20µA @5Hz, 60µA @20Hz, 110µA @40Hz — vs. 3.9mA for full gyro+accel+DMP operation, 3.8mA gyro+accel (DMP off), and 500µA accelerometer-only normal mode. Register-level: MOT_THR (Register 31, ~2mg/LSB) and MOT_DUR (Register 32, 1ms/LSB, 1kHz counter) configure the Motion Detection Interrupt; it operates independently of and alongside the Low-Power Accelerometer cycle mode.
- Source: InvenSense/TDK "MPU-6000 and MPU-6050 Product Specification" (multiple mirrored copies, e.g. cdiweb.com/datasheets/invensense/mpu-6050_datasheet_v3%204.pdf); register semantics cross-confirmed via i2cdevlib's MPU6050 class reference and esp-idf-lib's mpu6050 driver docs.
- Confidence: Established (primary manufacturer datasheet, cross-confirmed by two independent driver implementations).
- Relevance to SPARK: This is the mechanism to build the "sleep modes between windows" line in R-05's mitigation text into something concrete.

**Finding 2: A peer-reviewed design using this exact chip and pattern for wearable fall detection already exists and reports empirical battery-life numbers.**
- Evidence: Liu, Hou, He, Lungu & Dong, "An Energy-Efficient Fall Detection Method Based on FD-DNN for Elderly People," *Sensors* 20(15):4192 (2020), DOI 10.3390/s20154192 — open access, peer-reviewed. Uses the MPU6050 directly, driving free-fall (FF_THR/FF_DUR), motion (MOT_THR/MOT_DUR), and zero-motion (ZRMOT_THR/ZRMOT_DUR) interrupts in a 3-state finite state machine: idle → "motion state" (FIFO-buffered continuous 100Hz sampling, MCU low-power) → active transmission on free-fall/motion interrupt, returning to idle on zero-motion interrupt. Tuned values used: FF_THR=0.563g, FF_DUR=20ms (justified by weightlessness during a fall lasting <20ms per a cited source), ZRMOT_THR=0.5g, ZRMOT_DUR=1000ms. Measured result: a 600mAh battery sustained continuous operation for >30h in a worst-case always-transmitting test, and **140 hours (~17.5 days at 8h/day wear)** in a realistic wear test — versus what the paper frames as hours-scale battery life for always-on polling designs.
- Methodology/limitations: Host MCU is TI CC2530 (8-bit, 16MHz, ZigBee-integrated), not ESP32-S3; sampling rate 100Hz not 200Hz; this paper's algorithm structure (discrete FF/MOT/ZRMOT interrupts feeding a remote DNN classifier) is architecturally analogous to but not identical to SPARK's continuous-magnitude/duration-threshold gate. The 140h figure is specific to that hardware/battery/duty-cycle combination and does not transfer numerically to SPARK's ESP32-S3+1100mAh setup.
- Confidence: Established for the mechanism and pattern; Supported inference (not established) that SPARK would see comparable *proportional* gains, since ESP32-S3's baseline active draw (110–140mA) is far higher than CC2530's, so light-sleep quality on the ESP32-S3 side matters more than it did in this reference design.

### Bottom line
Yes, feasible, and well-supported. Published decision-level (late) IMU+RGB fusion work (Rehouma & Boukadoum, *Sensors* 2025) cuts false-positive rate from 11.3% (IMU-only) / 8.9% (vision-only) to 3.6% fused, at ~20 fps on **CPU-only** commodity hardware weaker than SPARK's gateway laptop — meaning SPARK's Acer Swift Go 16 (Core Ultra 7 155H, NPU+iGPU, currently spending only 200–383µs/window on the IMU CNN) has enormous headroom to spare for a second vision stream. The literature converges on two architecture families — mobile-robot-navigates-then-confirms, and stationary/room-camera decision-level fusion — and the latter is the correct fit for SPARK, since SPARK has no robot and already has a laptop gateway (§2.1 Layer 2) that could ingest a camera feed directly. Vision specifically corrects the failure mode SPARK's own Layer 1 hardware gate (simple 2.5g/300ms magnitude threshold, §2.5) is structurally prone to: abrupt-but-benign accelerometric impulses (quick sitting, dropped/bumped device, jumping) that spike magnitude without a real fall.

### Key findings

**Finding 1 — Decision-level IMU+vision fusion substantially cuts false positives without hurting sensitivity, on CPU-only hardware weaker than SPARK's gateway.**
- Evidence: N=16 healthy adults, waist-mounted IMU (50 Hz) + waist-height RGB camera at <5 lux (nighttime bedroom scenario), LOSO cross-validation, decision-level fusion (independent scores gated at threshold α=0.70). IMU-only (LSTM autoencoder): 90.3% acc, FPR 11.3%, AUC 0.931. Vision-only (Transformer over BlazePose 33-point 2D pose): 92.9% acc, FPR 8.9%, AUC 0.962. Fused: 97.2% acc, 97.8% recall, **FPR 3.6%**, AUC 0.989. End-to-end latency ≈50±4.7 ms/frame (~20 fps) on an **Intel Core i5-8265U, CPU-only, no GPU**, 8GB RAM.
- Source: Rehouma, H. & Boukadoum, M. "Fall Detection by Deep Learning-Based Bimodal Movement and Pose Sensing with Late Fusion." *Sensors* 25(19):6035, 2025. DOI: 10.3390/s25196035. Open access, PMC12526565.
- Confidence: **Established** (peer-reviewed, quantified methodology, statistically tested p<0.001).

**Finding 2 — Vision correction targets exactly SPARK's own Layer-1 weak point: simple-threshold false positives from non-fall accelerometric impulses.**
- Evidence: The fusion paper's own error analysis attributes its FPR reduction to vision suppressing "false positives from inertial impulses (e.g., abrupt sitting)," while IMU compensates when vision is degraded (occlusion/darkness).   **Source:** "Inertial Sensor Technology for Elite Swimming Performance Analysis: A Systematic Review," PMC4732051.

### Key findings

**Finding 1 — Apple Watch: wrist-worn, sensor-fusion algorithm, real-world accuracy well below the "seems reliable" assumption**
- Evidence: Uses accelerometer (magnitude of acceleration/jerk over a sliding ~0.2s window) + gyroscope (wrist-angle/orientation via sensor fusion) + optical heart-rate sensor (post-impact activity check) + barometer/altitude. Apple does not publish official accuracy figures.
- Source: <cite index="1-1">the fall detection algorithm is triggered if acceleration and jerk values exceed certain thresholds, then the device collects gyroscopic measurements, elevation, and heart rate information to determine whether a fall occurred, using sensor fusion and feature extraction to determine wrist angle and behavioral patterns like bracing, balancing, or flailing motions</cite> (Medium/Chendur Singaram, patent-based writeup); independent accuracy: <cite index="39-1,42-1,43-1">a systematic review and meta-analysis of 28 studies (1,226,801 participants) found pooled sensitivity of 81.9% (95% CI 75.1%-88.1%) and specificity of 62.5% (95% CI 14.4%-100%) for wearable-tracker fall detection specifically, based on only 3 of the 28 studies</cite>; separately, <cite index="41-1">independent testing by Consumer Reports found Apple Watch fall detection successfully identified only about 60% of severe falls in controlled simulations, dropping below 40% for less severe cases</cite>.
- Confidence: Established (peer-reviewed meta-analysis + independent consumer-org testing), though the fall-specific subgroup (n=3 studies) is small and specificity's 95% CI (14.4–100%) signals very high heterogeneity — treat the 62.5% point estimate as directionally useful, not precise.
- Relevance to SPARK: Undercuts any framing that "commercial wrist wearables already solve this well." SPARK's ≥90% sensitivity/≥90% specificity WP2 target (Track 4/5's concern) is meaningfully more ambitious than what independent testing shows even a mature, well-funded commercial product achieving. Good Ch1 sentence material: cite the gap between vendor confidence and independently measured performance.

**Finding 2 — Dedicated pendant systems: chest/neck placement preferred over wrist for accuracy; barometric pressure + accelerometer fusion**
- Evidence: <cite index="31-1">fall detection pendants have tiny sensors that detect changes in motion and height, analyzed in real time; fall detection works best worn on the outside of clothing close to the chest or waist area, where it can pick up motion patterns more accurately</cite>. Lifeline specifically: <cite index="25-1">the button uses accelerometers to measure sudden changes in force and barometric sensors to detect changes in pressure such as moving from standing to lying down, with an algorithm that determines whether the movement is a true fall or everyday activity</cite>.
- A 2026 wrist-vs-pendant head-to-head at one vendor found the wrist form factor underperforms: <cite index="21-1">a mobile pendant model detected zero test falls despite fall detection being confirmed enabled, while the wristband version of the same underlying system performed much better</cite> — direct evidence that sensor placement, not just algorithm, drives real-world reliability.
- An independent academic study (SmartFallMM) found combining sensors at two locations helps: <cite index="27-1">combining accelerometer data from the hip and the wrist yielded a model with an 88% F1-score using a Transformer network in offline evaluation, an 8-point improvement over wrist-accelerometer-only, but this model produced a high number of false positives when deployed in an uncontrolled home environment with streaming real-time data</cite>, and reducing that gap required active user feedback loops.
- Confidence: Established for vendor design guidance and the offline/online accuracy-drop pattern (peer-reviewed + hands-on reviewer testing); Supported inference that single-location wrist-only placement (SPARK's likely form factor, per tracker §2.2 enclosure lock) inherits some of this same real-world/lab accuracy gap unless mitigated.
- Relevance to SPARK: SPARK is wrist-worn (dorsal wrist frame per DATA_COLLECTION_PROTOCOL.md). This is a genuine, citable limitation to state candidly in Ch1/limitations rather than a reason to change hardware this late — the literature shows the offline-to-online performance drop is a known, general problem (not unique to weak vendors), and SPARK's two-layer gate (hardware threshold + CNN confirmation) is architecturally aimed at exactly this false-positive-in-deployment problem, which is a fair contrast to draw.

**Finding 3 — Marketing accuracy claims (~95%) are contradicted by documented failure incidents and a hardware recall**
- Evidence: <cite index="22-1">Philips Lifeline states its fall detection works only 95% of the time; the technology is best suited to picking up the drastic height changes of a standing adult suddenly collapsing but may miss subtler cases such as a wearer fainting and slowly slipping to the ground, or falling from less than 0.5 meters</cite>. This is corroborated by a real incident: <cite index="22-1">an elderly Lifeline-pendant wearer's slow slide to the bathroom floor was not detected by the auto-alert system, and the family later sued the company over the failure</cite>. Separately, a **hardware-level failure** occurred: <cite index="20-1">Philips Lifeline disclosed in November 2017 that a production issue affected AutoAlert Help Button devices shipped after August 1, 2017, preventing the automatic fall-detection function from sending a signal to the Emergency Response Center — the basic manual help button still worked, but automatic detection silently did not</cite>.
- Confidence: Established (company's own disclosed accuracy figure + company's own recall notice + reported litigation).
- Relevance to SPARK: Strong, specific Ch1 material — the failure mode (slow/gradual falls, e.g. fainting or controlled slides) is exactly the profile SPARK's tracker flags as a validity gap for its own *young-adult-simulated* fall data (Track 8's concern) — worth cross-referencing: commercial systems documented as weak on "slow" falls is external corroboration that this fall subtype is a known hard case industry-wide, not just a SPARK-specific dataset limitation.
